# AI 群友：身份与角色系统改造方案

状态：当前实施基线与后续最小改造范围

本文只解决一个问题：让机器人更像一个能自行判断的群友，而不是一套按配置表切换状态的客服机器人。

## 1. 产品定位

AI 群友应当：

- 持续保持虚拟人物的口吻和世界观；
- 根据上下文自行决定说不说、怎么说、说多少；
- 在被 @、被追问或需要帮助时自然参与；
- 没有必要时保持沉默；
- 不主动讨论 AI、模型或机器人身份；
- 不把虚构经历包装成现实世界可验证的事实。

身份披露不是运行时策略，不做配置，也不让模型在“承认 AI”和“隐藏 AI”之间切换。

## 2. 当前生产链路

```text
OneBot / NapCat
  -> Normalizer
  -> Presence Runtime / GroupActor
  -> ContextService.BuildSnapshot
  -> 轻量硬约束检查
  -> AgentPlanner / Composer / PromptSession
  -> Action Service / OutputGuard
  -> Canon prepare
  -> Outbound sender
  -> Canon after delivery
  -> TurnObserver.AfterTurn
```

`ContextSnapshot` 提供消息、群聊历史、关系、场景、Persona 状态和记忆；模型根据这些信息自行判断 `silent`、文字回复、玩笑、帮助、表情或其他允许动作。

## 3. 核心设计：模型自主，系统兜底

不再实现复杂的 `PresenceMode` 状态机，也不为 `observer`、`participant`、`helper`、`joker`、`moderator`、`withdrawn` 建立一套固定的行为配置矩阵。

这些词只作为上下文中的行为倾向：

```text
群聊氛围：轻松
当前关系：熟悉
最近状态：已经连续说过两次
角色倾向：偏 observer，必要时可以参与
```

最终由模型自主判断是否参与以及表达方式。

系统只保留不可交给模型的硬边界：

- 冷却时间和最大连续发言次数；
- 明确的群策略、用户禁用和权限限制；
- 工具白名单；
- 图片、戳一戳、撤回等动作校验；
- 输出长度、格式和安全检查；
- Canon 事实校验；
- action 幂等、发送失败和重启恢复。

原则是：**模型决定想不想说、怎么说；系统决定能不能发、能不能执行。**

## 4. 已完成

- 删除旧 `socialdecision`、旧 `presence/coordination`、旧 `presence/planning`、旧 Persona Context 和旧 Store Adapter。
- 统一到 `ContextSnapshot -> AgentPlanner -> Action Service` 主链路。
- 增加重复消息、低能量、撤回状态等基础拦截，但不把它们扩展成复杂角色状态机。
- 出站消息不再污染成员画像。
- 删除旧 Composer API 和旧状态接口。
- 移除身份披露配置，保持始终角色扮演。
- 删除旧角色决策相关文档和数据库表。

## 5. 必须改造的部分

本轮已落地 5.1～5.5 的最小版本；后续只在真实运行问题出现时继续加规则。

### 5.1 提升上下文质量，而不是增加角色配置（已落地）

继续完善 `ContextSnapshot`，但只加入模型真正需要的信息：

- 最近相关消息和当前话题；
- 是否直接 @、回复或点名；
- 当前群氛围和关系；
- Persona 的情绪、能量和说话倾向；
- 最近连续发言和冷却信息；
- 相关记忆及其来源。

不要把每一种可能行为提前写成规则表。

### 5.2 保留轻量硬约束（已落地）

Admission Gate 只负责低成本、不可违反的约束：

- 自己的出站消息不重复触发；
- 冷却和连续发言上限；
- 明确禁言或权限限制；
- 过期、重复或无效事件；
- 工具和动作安全检查。

低能量、observer 或 withdrawn 等信息可以作为模型上下文，不要默认直接替模型做决定。只有明确的安全或产品限制才拦截。

### 5.3 修复同群并发和发送幂等（已落地最小版本）

同一个群的旧模型请求不能在新消息之后晚到并发送过期回复。发送前需要检查事件是否仍然有效，动作需要稳定 `action_id`，失败重试不能重复发送。

### 5.4 补齐发送后的最小反馈闭环（已落地最小版本）

发送成功后记录 `action_id`、平台消息 ID 和发送时间。后续只有在明确回复、@、引用、追问或纠正时才认为存在反馈。

第一阶段只做可靠归因和关系事件记录，不急着引入复杂的情绪评分、群接纳度模型或新的反馈数据库。

### 5.5 修复上下文传递和失败降级（已落地）

- Composer、记忆检索和约束构建使用真实请求上下文；
- 模型超时可以沉默或走简单 fallback；
- 记忆失败不应阻断普通回复；
- Canon 校验失败不得发送；
- Action 失败不得假装成功。

## 6. 暂不做

以下内容当前会增加复杂度，暂不作为改造目标：

- PresenceMode 配置矩阵；
- 角色转移状态机；
- 让大模型输出并修改自己的角色权限；
- 独立的决策数据库或 Turn Journal；
- 复杂的长期反馈学习和群接纳度评分；
- 主动发言调度器；
- 为每种角色建立独立 Prompt、独立 Store 或独立服务。

如果未来确实出现可复现的问题，再针对具体问题增加最小约束，不提前搭建完整框架。

## 7. 验收标准

### 自主性

- 普通闲聊时模型可以自然选择沉默；
- 被直接提及时可以自然回应；
- 同一角色不需要每次做出相同动作；
- 模型可以自行选择简短回答、玩笑、帮助或沉默。

### 边界

- 模型不能绕过冷却、权限、工具白名单和 OutputGuard；
- 出站失败不能产生“已发送”的事实；
- 机器人自己的消息不进入成员画像；
- 虚构内容不能被写成现实可验证的 Canon 事实。

### 稳定性

- 同群新消息不会被旧模型结果覆盖；
- 同一进程内重试不会重复发送；跨重启恢复仍依赖后续 Outbox/发送回执设计；
- 记忆、画像或模型服务局部失败时有明确降级行为。

## 8. 数据边界

以下旧表已经从 schema 和运行数据库删除：

- `group_persona_postures`
- `group_persona_ephemeral`
- `participation_decisions`
- `action_feedbacks`
- `feedback_windows`

当前继续使用 `runtime_states`、`thought_records`、`relationship_events`、`group_working_memory`、`memories`、Persona Canon 和 Outbox 相关表，不再恢复旧决策表或旧反馈表。

## 9. 实施顺序

```text
上下文质量（已完成）
  -> 轻量硬约束（已完成）
  -> 并发取消与发送幂等（已完成最小版本）
  -> 最小反馈归因（已完成最小版本）
  -> 上下文传递与失败降级（已完成）
  -> 针对真实问题补充最小规则
```

每一步都应有对应测试和运行证据。除非出现明确问题，不再继续增加角色配置、状态机或持久化层。
